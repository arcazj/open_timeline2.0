# Configuration Catalog Release Contract

This contract implements REQ-06 and REQ-20-22 without changing the JSON-only storage boundary. It supplements, rather than narrows, the modernization specification. Implementation and test status are recorded separately in the release checklist.

## Portable Representation

Retain the existing snapshot `models`, `filters` and `settings` fields. Add optional `sources`, `groups`, `schemas`, `views`, `preferences` and `defaults` fields to the version-1 snapshot. New exports include normalized catalog fields. Older complete snapshots are integrity-checked before normalization; missing source resources are derived from the declared source IDs, not just loaded records. Missing groups are derived from all record group references. Empty legacy filters remain empty. Unsupported nonempty legacy filter definitions require the migration adapter and explicit diagnostics, not silent deletion.

There is one canonical array for each resource family; do not maintain a second filter/model authority. Snapshot integrity covers every present portable catalog field, including private resources admitted to the declared export scope. Absent optional fields must not change verification of existing snapshot hashes. Normalization invalidates the old checksum and the next complete export computes a new one.

All new definitions use JSON Schema 2020-12. Existing draft-07 schemas are migrated and validated together before activating the new contract; do not mix unsupported schema dialects in an Ajv instance. The HTTP schema baseline remains OpenAPI 3.1.1.

## Resource Envelope

Sources, groups, data schemas, saved filters and saved views follow the established visual-model envelope: `id`, `name`, `description`, `tags`, `revision`, `lifecycle`, `createdAt`, `updatedAt`, nullable `draft`, and contiguous immutable `versions`. Add `formatVersion: 1`, `ownerId`, `visibility` (`personal` or `workspace`) and nullable `copiedFrom` provenance. New IDs are provider-assigned UUIDs; declared legacy source/group IDs remain stable on normalization. Existing visual-model IDs and published definitions also remain unchanged.

Each publication contains `version`, `publishedAt`, `publishedBy` and `definition`. A source/group begins with a published definition; schemas, filters, models and views may begin as drafts. Publishing never implicitly changes a record, saved view or active setting pin. Metadata revision and definition version are distinct. Maximums are 100 resources per family, 32 publications per resource, 100 name codepoints, 2,000 description codepoints, 20 tags, and 64 KiB per resource definition. Capacity failures reject the whole command and never truncate history. Limits remain advertised and may be raised only with corresponding admission tests.

Source definitions are logical JSON namespaces, not filesystem paths or connectors. They contain `storage: "json"` and an optional pinned default data schema. Group definitions contain a stable display order, optional approved color and default collapsed state. Retiring a source/group does not erase records or remove it from complete-snapshot scope. New references to archived resources are rejected; existing references remain readable.

Data-schema definitions contain a bounded JSON Schema for a record's `data`. Core record properties cannot be redefined. Remote resolution, executable expressions, arbitrary regular expressions and recursive references are forbidden. Approved local references must be acyclic and complexity-bounded. Schema versions remain pinned on active and restorable records. A schema's impact endpoint reports affected IDs/counts and validation failures before any explicit migration.

Saved-filter definitions contain the shared typed expression tree, source/kind predicates, explicit schema/version scope, and contextual search settings. Search remains a separate projection rather than a destructive filter. Saved-view definitions pin a model and optional filter and contain mode, range/overview, grouping/collapse state, timezone, column visibility/order/width and stable table sort. All referenced pins are checked before publication and application.

## Commands and HTTP

Use the same provider interface in both modes: list/get/validate/usage for a family, a captured immutable command for create/update/publish/archive/unarchive/delete/duplicate/apply, and explicit source-scoped outcome lookup. API collections are `B/sources`, `B/groups`, `B/schemas`, `B/filters` and `B/views`; metadata and definition history are not record projections. Add `/{id}/versions`, `/{id}/versions/{version}`, `/{id}/publish`, `/{id}/archive`, `/{id}/unarchive`, `/{id}/usage`, and appropriate preview/apply/impact routes.

Every durable command uses request-local authenticated identity, workspace generation, resource ETag and idempotency identity. PUT replaces the declared mutable representation, PATCH is allowlisted JSON Patch, and DELETE is reference-safe. Source/group membership and manifest scope change in the same transaction. A record cannot observe half of a catalog update. Local commands use identical validation and reference rules but commit only to source-scoped memory.

Visibility is enforced before listing, preview, validation of references, mutation or outcome replay. Personal resources are managed by their owner; shared publication requires explicit capability. Shared defaults cannot reference a private resource. Local ownership metadata is provenance, not proof of server identity or permission. Importing a Local snapshot never grants its claimed permissions to a server principal.

## Reference Graph and Settings

Reference checks include active records, tombstones, every immutable publication, saved filters/views, source schema defaults and workspace/personal pins. Usage results identify the referencing resource and version without exposing an unauthorized private definition. A referenced publication is immutable and cannot be deleted. Archival preserves references. Renames/type changes/required-field additions need an explicit impact preview and bounded migration; no implicit record rewrite occurs on publish.

Settings resolve in order: application defaults, workspace defaults, the selected visual model, saved-view overrides, personal overrides, then transient interaction state. Hard server limits and capabilities constrain every layer. Allowed scalar keys replace, declared maps merge by key, and arrays replace. Reset removes an override; it is not equivalent to a nullable explicit value. Provide effective values plus per-key provenance through an inspection endpoint and the UI. Startup roots, bind addresses, secrets and transport policy are not mutable browser settings.

Workspace/application settings, personal preferences and view application each have their own generation/revision preconditions. Applying a view is atomic, preserves open drafts until explicit user resolution, and refreshes both renderers from one new query snapshot. Temporary search/pan/page changes do not silently publish a shared resource.

## Required Evidence

Tests must cover both providers, HTTP permissions, immutable publication, every reference edge including tombstones, duplicate provenance, conflicting edits, no partial persistence, original-outcome recovery, private-resource disclosure, complete export/import with new and old hashes, settings provenance/reset, and browser authoring/application of every family. Renderers must remain independent of provider type. A management API without usable corresponding authoring and inspection screens does not complete this requirement.

## Shared Core Wire Contract

This section freezes the shared pure JavaScript/Python catalog representation. It is not a claim that the HTTP, provider or UI integration has shipped. A new, separate Ajv 2020-12 validator may validate these resources while existing draft-07 validators remain separate; activating portable snapshots containing them requires the coordinated snapshot-validator migration described above.

An authenticated caller supplies `actor: {id, capabilities}`. Capabilities are strings `configuration.read`, `configuration.personal`, `configuration.publish`, `configuration.manage`, or `*`. The explicitly constructed Local actor may receive `*`; imported ownership/visibility never supplies capabilities. Read admits workspace resources and the actor's personal resources; management admits all resources. Personal mutations require the owner and `configuration.personal`; workspace mutations require `configuration.manage`; publishing a workspace definition additionally requires `configuration.publish`. `*` satisfies every capability. Unauthorized resource identities behave as unavailable. Sources and groups are workspace resources because record membership must not depend on a private catalog entry.

Definitions use these exact fields, with all listed fields required unless marked optional:

- Sources: `{storage: "json", enabled: true, writable: true, defaultSchema: null | {id, version}}`. Disabled sources remain readable and in snapshot scope but admit no new writes. `writable: false` blocks record mutations, including restore and tombstone changes. Source definition publication does not migrate existing record schema pins.
- Groups: `{order: 0, color: null | "#RRGGBB", collapsed: false}`. Order is a safe integer. Existing record `groupIds` retain their order and identity.
- Schemas: `{schema: <bounded JSON Schema 2020-12>}`. The root is an object schema for `record.data`, with `properties` and `additionalProperties: false`. Built-in optional properties description/text/system/type/status are strings and priority is numeric; they are automatically admitted if omitted, cannot be incompatibly redefined, and do not become required implicitly. Custom properties and nested objects/arrays may be declared. The bounded dialect admits `$schema`, `$defs`, `$ref`, `type`, `properties`, `required`, `additionalProperties`, `items`, `enum`, `const`, `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `minLength`, `maxLength`, `minItems`, `maxItems`, `uniqueItems`, `minProperties`, `maxProperties`, `title`, and `description`. Local references use `#/$defs/<name>` only, without sibling keywords, with no cycles. Only JSON primitive/object/array/null types are admitted; type unions may add null to one other type. No regular expressions, remote resolution, arbitrary formats, composition or executable keywords are admitted. Bounds: 64 KiB UTF-8 definition, 256 schema nodes, 16 structural/ref levels, 100 properties per object and 100 enum values. Unsupported keywords are errors, not ignored annotations.
- Filters: `{sourceIds: null | [id], kinds: ["event", "session"], schemaRefs: [{id, version}], expression: null | {version: 1, root}, search: {text, mode, caseSensitive, fields}}`. Source IDs and schema pins are unique. `sourceIds: null` means all declared sources; `[]` means none. `kinds` may also be empty. A nonempty `schemaRefs` list restricts the result to records carrying exactly one of those schema/version pins; an empty list imposes no schema restriction and exposes built-in fields only. The expression is then evaluated within that scope. All schema versions in a mixed scope must declare a used custom field with the same type; incompatible/missing declarations reject the filter. Search is a contextual projection over this result, not a second destructive predicate. Search fields are JSON Pointers; mode is `any`, `all` or `phrase`; text is bounded to 512 codepoints. The existing shared filter/search parser supplies operator, escaping, null, casefold and complexity semantics.
- Views: `{model: {id, version}, filter: null | {id, version}, settings: <overrides>}`. Model/filter pins live in these fields, not duplicated inside `settings`. A view cannot contain another view pin. Published references remain exact even after later publications.

Allowed settings keys are the existing visual definition keys (`theme`, `rowHeight`, `fontSize`, `groupBy`, `displayUnit`, `timeZone`, `scaleMode`, `ratio`, `bins`, optional `presentation`), plus `mode` (`timeline`, `table`, `split`), `range`, `overview`, `referenceTime`, `collapsedGroups` (unique group IDs), `columns` (an ordered array of `{field, visible, width}`), `sort` (1-3 `{field, direction}` entries), and `search` in the filter search shape. Range/overview retain `{from,to}` offset timestamps with `from < to`; detail must fit overview once layers resolve. Column width is an integer 44-2000 CSS px, at most 32 unique field names. Sort direction is `asc`/`desc`; duplicate sort fields are rejected. Field names are the existing canonical table names or declared `/data/...` pointers. A settings override is a partial object; absent keys reset by omission, arrays replace, and range/overview/search merge by key. Empty partial objects never erase a lower layer.

Workspace `defaults` is `{revision, values}`; `preferences` is an array of `{principalId, revision, values}` with one entry per principal. Their values may additionally contain existing paired `modelId`/`modelVersion`, and paired nullable `filterId`/`filterVersion`, `viewId`/`viewVersion`. A null pin requires both fields null. Existing `snapshot.settings` is the portable active settings and legacy workspace base; `defaults.values` overlays this base without creating a second model/filter catalog. Missing defaults/preferences normalize to revision 1 with empty values / an empty array. Effective resolution is application defaults, workspace active/base plus defaults, selected model definition, selected view overrides, selected principal overrides, transient state. A personal/transient model or view pin selects the model/view used at their normal precedence level; it does not change the precedence of the remaining fields. Explicit view selection supplies that view's model/filter pins. The inspector returns `{values, origins}` with origins keyed by JSON Pointer to each leaf, including array-valued leaves. Transport policy, filesystem roots and secrets are never accepted settings.

Commands use `{family,type,resourceId?,expectedRevision?,expectedPreferenceRevision?,generation,clientCommandId,payload?}`. Families are `sources`, `groups`, `schemas`, `filters`, `views`. Create payload is `{name,description?,tags?,visibility?,definition}`. Update payload may replace `name`, `description`, `tags`, or `draft`; it cannot mutate ownership, visibility, history or identity. Publish/archive/unarchive/delete have empty payloads. Duplicate payload is `{name,version?,visibility?}`; omitting version copies the current draft if present, otherwise the latest publication, into a new draft (source/group copies begin published). Provenance is `{family,id,version: integer | null}`; no source definition contents are copied into provenance. Apply is defined for filters/views only, payload `{version}`; source/group changes apply through their latest published identity-level policy, while schema adoption requires explicit record migration. Apply updates only the acting principal's preference pins atomically, never shared `snapshot.settings`, does not alter the resource revision or publish a definition, and returns effective settings. Apply additionally requires `expectedPreferenceRevision`: absent preferences have revision 0, first application creates revision 1, existing preferences increment once; a missing precondition is 428 and a stale value is 412 `configuration_preference_revision_conflict`. Effective settings return `preferenceRevision` alongside values/origins. Shared defaults require a separate explicit manage operation. Canonical shared records may pin only workspace-visible data schemas; personal schemas remain available for draft authoring and preview until explicitly duplicated/published into the workspace.

The pure operation clones the input and never changes the caller's snapshot or command. It validates explicit generation (missing 428, mismatch 409) and resource revision (missing 428, mismatch 412). Create/duplicate IDs come from the injected provider UUID generator; updates increment resource revision once. The enclosing provider alone advances the workspace revision, verifies/replays idempotency, persists outcome/audit and enforces snapshot byte limits. Replayed commands must be resolved before re-running this pure operation. Definition errors are 422 `invalid_configuration_definition`; envelope/command errors 422 `invalid_configuration`; forbidden operations 403 `configuration_forbidden`; unavailable identities 404 `configuration_not_found`; missing versions 409 `configuration_version_unavailable`; referenced deletion 409 `configuration_referenced`; archived writes 409 `configuration_archived`; capacity exhaustion 413 `configuration_capacity`.

Normalization preserves existing model IDs/publications through the established model normalizer; source/group definitions missing from old snapshots are synthesized at `manifest.snapshotAt`, owner `legacy-import`, visibility workspace, published by `legacy-import`, revision/version 1. Source IDs derive from the complete manifest scope, groups from all active and tombstoned records. Existing nonempty unknown legacy filters fail with migration-required diagnostics. Canonical source identities must equal manifest source scope; create/delete source changes that scope in the same returned snapshot. Archived sources stay in scope. All mutations remove the old `contentSha256`; normalization removes it only when portable content actually changes. Integrity verification belongs before normalization.

`configurationUsage` is an internal full-graph operation, including tombstones, drafts, every historical publication, source defaults, saved views/filters, workspace and personal pins. It returns reference descriptors, not definitions. A provider must authorize/redact this result before disclosure; unauthorized private descriptors and counts must not leak. Delete checks the unredacted graph. Existing archived references are valid on import/read; creating, publishing or applying a new reference to an archived resource fails. Visibility checks reject workspace-to-personal references and cross-owner personal references. `filterFieldTypes(snapshot, schemaRefs)` returns the shared built-in registry plus compatible declared custom JSON Pointer fields for query-compiler integration; catalog admission alone does not activate custom filtering in an older query compiler.

Existing source/group IDs are retained as nonempty strings of at most 128 codepoints, including punctuation and Unicode, without interpreting them as filesystem paths. Automatically derived display names use the first 100 codepoints or `Imported source`/`Imported group` for an otherwise blank label; identity is never truncated. New IDs remain provider-assigned UUIDs. An explicitly present null catalog is invalid, not equivalent to an absent legacy field.

The selected saved filter's search settings contribute immediately after the selected model and before saved-view, personal and transient overrides. Their provenance is `filter:<id>@<version>`. Other precedence rules are unchanged. Sort fields must be declared scalar fields, not arrays. Apply returns `resetTransientKeys`: selection-pin keys plus the authored view settings keys, and `search` when a saved filter is being selected; these are instructions to clear transient overrides only, not to delete unrelated personal preferences. `defaultConfigurationDefinition(family, snapshot)` supplies a fresh supported authoring template; view defaults require the normalized model pin. `resolvedDataSchema(definition)` supplies the validated schema plus built-in data fields for record validation/impact; catalog normalization verifies record references but the provider still validates each record payload through the applicable resolved schema before admission.

View-selection pins retain the provenance of the layer that selected them: workspace, personal or transient. They are not labelled as coming from their own view definition. Explicit `viewId`/`viewVersion` preview arguments must be supplied together, receive `preview` provenance, and paired null values clear the returned view pins even when a personal view was previously selected. Model/filter pins derived from a selected view retain that view's provenance. This distinction makes a personal view selection inspectable and resettable without mislabelling it as an immutable published field.

## Provider and UI Wire Envelopes

The following shapes are frozen for the implementation. They contain the active provider's `generation` and committed workspace `revision`; Local commit durability is explicitly `memory`, Server durability is `json-files`.

- `listConfiguration(family, {includeArchived: true}, options)` returns `{family, generation, revision, items, total}`. Items are authorized metadata summaries, not complete definition histories: envelope metadata plus `hasDraft`, `publishedVersions: [number]`, and `allowedActions: [string]`. Name/codepoint ordering has ID as a tie-breaker. The current 100-resource family bound permits one complete bounded metadata response; total counts only visible resources.
- `getConfiguration(family, id, options)` returns `{family, generation, revision, resource, allowedActions}`. Resource contains the full authorized envelope/history. A missing or inaccessible identity is unavailable; it does not return a redacted private definition.
- `validateConfiguration(family, definition, context, options)` returns `{valid, errors}`. Errors are `{path, code, message}` using JSON Pointers into the submitted definition. Context may contain `resourceId` and proposed `visibility`; authenticated actor/ownership are server-resolved, not accepted as permission claims. Validation is read-only.
- `configurationUsage(family, id, version, options)` returns `{family, generation, revision, items, total, deletionBlocked}`. Items contain only authorized reference descriptors. Total counts the disclosed items only. The boolean is the resource's reference-safety result, not a private-reference count. Do not infer deletion permission from an empty disclosed list. Resource family bounds and record references require cursor pagination at 100 items (maximum 1,000), with `nextCursor` when needed; the provider may accept an additional `cursor`/`limit` options object.
- `mutateConfiguration(command, options)` returns `{status: "committed", durability, commandId, family, generation, revision, resource, effectiveSettings?}`. Deleted resources are null. Use original command outcome lookup for uncertain replies; never retry with another identity automatically. Apply returns effective settings for the acting principal, with `resetTransientKeys` naming the keys authored by the applied view/filter. The UI removes only those transient overrides before rendering the applied values. Unrelated selection remains subject to the new source/filter and unsaved drafts require explicit resolution.
- `getEffectiveSettings({viewId?, viewVersion?, transient?}, options)` returns `{generation, revision, principalId, values, origins}`. Origins follow the pure-core JSON Pointer map. The requested principal is always the active actor, except an explicit administrator inspection route. Returned values are effective settings, not all other users' preferences.
- `mutateSettings({scope,type,expectedRevision,generation,clientCommandId,payload}, options)` supports `scope: "personal" | "workspace"` and `type: "patch" | "replace" | "reset"`. Patch/replace payloads are validated override objects; only range, overview and search maps merge by key, while arrays replace. Reset payload is `{paths:null}` for all overrides or `{paths:[JSONPointer,...]}` for distinct admitted leaves. Paired model/filter/view pins must remain valid together. Personal revision starts at zero when no entry exists; workspace defaults start at one. Missing revision is 428, stale revision is 412. Personal writes require `configuration.personal`; workspace defaults require `configuration.manage`. Application/root settings are not admitted by this command. Result is `{status:"committed",durability,commandId,generation,revision,settings,effectiveSettings}`. The durable Server route is `POST B/settings/commands`, with matching generation/idempotency headers and `If-Match: "generation:expectedRevision"`. A replay returns its original outcome; the entire settings change and workspace revision commit together.
- `previewSchemaImpact(schemaId, {version?, definition?, cursor?, limit?}, options)` is read-only and returns `{generation, revision, schemaId, totalAffected, totalInvalid, items, nextCursor}`. Exactly one candidate published version or draft definition is supplied. Items contain authorized record IDs, current pins and bounded field-level errors. A complete immutable analysis precedes exact totals; paging does not change the analysis. This is an impact preview, not permission to migrate records. Applying a migration uses the separately authorized bounded job/batch flow.

`initialize`/`getStatus` additionally expose `actor: {id, name, capabilities, sourceIds}` for the current workspace and the active principal's effective `settings`. Local actor grants are explicitly created by the Local provider and are labelled unverified/local; imported owners are not verified identities. UI controls use `allowedActions` and capabilities, but the API rechecks every operation inside its commit boundary.

Source/group creation and duplication include initial publication, therefore require both `configuration.manage` and `configuration.publish` (or `*`). Later draft editing requires manage; publishing requires both. Personal schema/model/filter/view publication requires ownership plus `configuration.personal`; adopting a schema on canonical workspace records requires a workspace-visible published schema. Explicit workspace publication/duplication remains capability-checked.

Catalog dialogs provide list/detail, structured definition editing with a strict JSON alternative, publication history, reference inspection, explicit apply where meaningful, archive/unarchive, reference-safe deletion and definition import/export. Source policy uses real toggles, colors use swatches, ordering uses steppers/move controls, and schema impact is a separate read-only view. Effective-settings inspection exposes per-field origin and reset-to-inherited controls. No placeholder commands are shown for an unimplemented operation.
