# Configuration UI Integration

The configuration manager consumes the frozen provider envelopes in `configuration-catalog-contract.md`. Management controls use returned `allowedActions` and the active actor's capabilities. The API remains the authorization authority. Sources/groups require manage and publish capabilities for creation and duplication because those operations include an initial publication.

Definition interchange uses exactly `{format:"timeline-configuration",formatVersion:1,family,name,description,tags,visibility,definition}`. Unknown keys and duplicate JSON properties are rejected. Import creates a new resource identity; it never overwrites a catalog entry or imports permission grants.

Applying a filter/view includes both the captured resource `expectedRevision` and `expectedPreferenceRevision`. An absent personal preference has revision 0. The result affects the acting principal, not shared workspace settings. The host applies returned effective values after removing only `resetTransientKeys`; it preserves unrelated interaction state and requires explicit resolution of unsaved drafts.

Effective-setting reset uses `mutateSettings({scope,type:"reset",expectedRevision,generation,clientCommandId,payload:{paths}})`. `paths` is a list of JSON Pointers; null removes all overrides in that scope. The first personal write creates revision 1. The response contains `{status:"committed",durability,commandId,generation,revision,settings:{revision,values},effectiveSettings}`. Reset controls are available only when the provider and active-view application callback are integrated.

The active application now integrates Apply and reset. Model/filter/view identity and version are reset as pairs. Only genuine UI edits populate the transient settings layer; merely reading inherited settings does not create overrides. Effective inspection includes that layer with `transient` provenance. Apply keeps temporary navigation unless the selected view authors the affected range/overview, and keeps other temporary visual settings unless the returned reset list names them. Saved-filter predicates intersect source/type/temporary conditions; schema-scoped fields come from the authorized selected publication. Application-default search retains the legacy six fields, while explicitly authored field lists remain exact.

Saved table columns control visibility, order and pixel width. Up to three scalar sort descriptors are applied by the provider across the full query, not per page. Boolean and numeric custom fields retain their types; arrays can be displayed but not sorted. Canonical group collapse remains open release work: a nonempty `collapsedGroups` view is rejected during read-only Apply preflight, before preferences change. It is not silently ignored.

Complete JSON export hashes `snapshotContent`, including the expanded catalogs. Supported temporary settings are merged only into the active principal's preference entry in the downloaded copy; shared workspace settings and other owners remain unchanged. Importing a Server export as Local does not impersonate its principal or adopt its private preferences. Local authors explicitly duplicate/apply a portable view when appropriate. Temporary source/type selectors and ad-hoc conditions remain query state, not fabricated published configuration.

Uncertain configuration/settings writes retain only source, workspace, generation, principal, command, family/type, optional resource identity and settings scope. Tokens, definitions, values and patch paths are not persisted. Reopening or reloading resolves the original command through a user-triggered read-only outcome request, never an automatic retry. A principal change cannot transfer another principal's pending identity or mutation lock. Storage denial and file-URL retention uncertainty are disclosed.

The host opens the manager with captured `provider`, `generation`, `actor`, `local`, `models` and `isCurrent` values. `onMutation(result)` updates confirmed metadata; `onApply(effectiveSettings, resetTransientKeys)` updates the active view; `transientSettings()` supplies actual client overrides; `validateApply({family,resource,version,definition})` performs read-only compatibility checks before dispatch. A confirmed command is installed in editor state before optional host refresh, so a follow-up read failure cannot turn it into another create. A late confirmed response still notifies its original active source after editor closure, without touching a different source. Main query/navigation changes are owned by the application integration, not the manager.
