# Legacy Menu and Search Audit

## Scope and Evidence

This document supports the revision 2.2 specification for a compact legacy-like menu bar, yellow backgrounds on matching labels, contextual detailed bands, and overview bands containing only matching findings. It is a static source audit, not a claim that the legacy application was built, run, or visually verified. Replacement contracts below are proposed requirements, not descriptions of existing reliable behavior.

The audited repository is `arcazj/openbexi_timeline`, pinned to commit `cf5d263853e550aab44d3d1959637c1e324b719e`. Paths and line numbers below refer to that revision. The [model compatibility inventory](legacy-model-compatibility.md) and [interaction audit](legacy-interaction-audit.md) remain companion inputs. This audit does not introduce application code, database connectors, or persistence changes.

## Grouping and Filter Controls

The filter panel includes a `Sort by` select, Apply and Close commands, saved-filter radio choices, name/expression editors, and edit/save/delete/help affordances. Add, read, update, save, and delete operations are passed to `ob_load_filters`. The saved state includes `sortBy`, filter text, name, background, dimensions, camera, timeline name, and user/email. Selecting a filter calls `ob_update_filter`; do not infer that every legacy select action is read-only. `src/openbexi_timeline.js:561`, `:582`, `:630`, `:637`, `:726`. [Filter actions][filter-actions] [Filter persistence][filter-persistence] [Filter rows][filter-rows] [Filter panel][filter-panel]

The available grouping choices come from discovered field values, with a restrictive heuristic: at least two values, fewer than fifteen values, and short field/value names. Applying non-`NONE` grouping hides both overview buttons. These restrictions are legacy defects/limitations to correct, not compatibility obligations. The new model schema must expose eligible grouping fields deliberately; grouping, ordering, filtering, and search are separate operations, and grouping must not disable overview search. `src/openbexi_timeline.js:399`, `:473`. [Group apply][group-apply] [Group options][group-options]

Filter help documents include/exclude syntax and examples using `=`, `;`, `|`, and `+`. Filter input also undergoes character stripping and sentinel substitutions. The client has a separate regex-building path applied to ID-less activity titles. These are distinct from header search and must not be combined into an undocumented query language. Preserve imported filter intent through the structured, versioned filter adapter; reject unsupported expressions with diagnostics. `src/openbexi_timeline.js:492`, `:512`, `:3647`, `:3723`. [Filter help/input][filter-input] [Client filter][client-filter] [Record rendering][record-render]

## Legacy Search Trace

1. Search is initialized to an empty string when absent. Header icon click and Enter apply it; the audited input registers `onmousemove` and `onkeydown`, but no clear/search/input listener. Clearing the browser's native search field is therefore not explicitly wired to refresh results until a command is applied. Search reset preserves the marker time as the synchronization anchor; it is not a first-hit navigation implementation. `src/openbexi_timeline.js:306`, `:196`, `:1388`, `:1546`. [Initial state][initial-state] [Time reset][time-reset] [Search button][search-button] [Search input][search-input]
2. Data requests concatenate `startDate`, `endDate`, `filter`, and `search` into the URL. Search is not encoded with a structured URL builder in this path. The JSON backend reads files, applies `filterDates`, then include/exclude `filterEvents`, and finally `searchEvents`. Thus it searches the loaded, date-filtered, filter-eligible collection, not a demonstrated complete workspace-wide search index. `src/openbexi_timeline.js:4693`; `src/com/openbexi/timeline/data_browser/json_files_manager.java:103`. [Request][request] [Read pipeline][read-pipeline]
3. `searchEvents` replaces semicolons and spaces with regex alternation. It compiles a case-sensitive Java regex and uses `find()` over each record's serialized JSON with spaces and quote characters removed. Search therefore includes serialized keys, IDs, dates, and render metadata as well as descriptive data. For objects with `activities`, only activities are examined; the enclosing object's own fields are not independently matched. `json_files_manager.java:418`. [Server search][server-search]
4. On a match, it writes `render.backgroundColor = "#F8DF09"` into the response object. Flat records also receive `render.next_date`; activities do not. It fills `new_events` but never returns that array. The returned `new_events2` is always assigned the original `events` array, which now contains the in-memory highlight mutations. This function itself does not write files. Every normal `getData` read reparses source JSON, so a subsequent request normally replaces these transient styles; no explicit restore-original-background algorithm exists in `searchEvents`. `json_files_manager.java:107`, `:422`, `:434`, `:445`, `:456`. [Read pipeline][read-pipeline] [Server search][server-search]
5. Detailed bands always draw eligible activities, whether matched or not. Overview bands draw a point/session only when the search is empty or its label background equals `#F8DF09`. A render override's `backgroundColor` supplies the label background, while its `color` supplies the event/session glyph color. The label renderer colors the whole text sprite background and uses dark foreground text; it is not substring-only glyph recoloring. `src/openbexi_timeline.js:3740`, `:3757`, `:3770`, `:4138`. [Record rendering][record-render] [Label rendering][label-render]
6. Overview parent enclosures use a different property, `render.textBackgroundColor`, and may be added once per child. The lower-level event/session functions also test `_overview`, whereas the dispatch branches test `overview_`. Yellow-square assets and reduced sizes appear in the lower-level search branches, but these differing name checks mean this is not evidence of reliable rendering for every overview name. `src/openbexi_timeline.js:3786`, `:3901`, `:4011`. [Parent rendering][parent-render] [Overview session][overview-session] [Overview event][overview-event]

### Defects Not to Preserve

| Risk | Evidence and required correction |
| --- | --- |
| False or unsafe matches | Raw regex, stripped spaces, and complete serialized JSON search cause unexpected matches. Repeated separators can introduce empty alternatives; malformed patterns can throw; pathological patterns can consume excessive work. Use bounded literal search semantics, not user-supplied regex. [Server search][server-search] |
| Missing render object | A matching record with no `render` dereferences null; the outer read path catches errors and can substitute dummy data instead of a useful search error. Highlighting must work on records with no visual overrides. [Server search][server-search] [Read pipeline][read-pipeline] |
| Style mistaken for membership | A pre-authored yellow label can appear in overview as a match despite not matching the query. Use explicit match IDs/metadata, never color equality. [Record rendering][record-render] |
| Inconsistent empty/wildcard behavior | `*` bypasses server matching but remains a nonempty client query, so overview can hide all normal records. Define empty query separately; treat regex/wildcard punctuation literally unless a separately specified advanced mode exists. [Server search][server-search] [Record rendering][record-render] |
| Parent/child errors | Parent fields are skipped when `activities` exists; overview enclosure reads the wrong background key and can duplicate enclosures. Each canonical record matches independently; relation context must not silently become a finding. [Server search][server-search] [Parent rendering][parent-render] |
| Missing lifecycle contract | No explicit match counts, matched fields, query identity, clear handler, reliable next/previous workflow, or style-restoration contract is established. Require these independently of rendering details. [Search input][search-input] [Server search][server-search] |
| Cross-instance/UI fragility | Absolute positioning, non-button image controls, unlabelled search label creation, global-style IDs in filter controls, and header dragging invite focus, overlap, and instance-scoping failures. Use scoped state, real buttons, accessible labels, responsive layout, and separated pointer targets. [Header][header] [Filter panel][filter-panel] [Search input][search-input] [Placement][placement] |

## Recommended Replacement Contract

### Compact Menu

- Keep the main timeline's menu compact and visually subordinate to its bands: a single restrained desktop toolbar, familiar icon buttons, a directly usable search field, and a small time/status display. Preserve the command meanings above; do not relabel the connection icon as play/pause or the camera icon as Timeline/Table.
- Use native button semantics, accessible names, visible keyboard focus, tooltips, explicit pressed states, disabled/loading/error states, and adequate touch targets. A connection indicator reports actual transport state; it does not imply that local data is authenticated or saved.
- Keep grouping/filter, model management, settings, and help behind compact commands or menus. New Timeline/Table and create controls must remain available without turning the header into a row of large text cards. A visible title/model selection can be concise; a full model editor belongs in its own authoring surface.
- Use responsive tracks and an overflow menu for secondary commands. Search and active state must remain discoverable at narrow widths and 200% zoom, with no icon/text collisions. Activating, selecting text in, or scrolling a toolbar control must not initiate timeline drag, move a floating panel, or persist a record.

### Query and Membership

- Let `B` be canonical records authorized for the current workspace and source/schema scope after saved structured filters and any explicit user-selected time predicate. A viewport loading window alone does not change `B`. Let `M` be IDs in `B` that match the active search. Default search scope is the full filtered set, not merely loaded rows; an explicit visible-range search mode may narrow it. Return the scope, query identity, workspace generation/revision, match count when exact, and cursor/snapshot identity with results.
- Detailed timeline bands render their visible slice of `B` and preserve nonmatching context; only records in `M` get the yellow label overlay. With an active nonempty query, every overview band renders only its in-range slice of `M`. With an empty query, overview returns to its normal filtered representation of `B`. Offscreen findings remain available through count and navigation; clipping a mark is not deleting it from the result set.
- Overview-only findings means no nonmatching record glyphs, density contributions, parent enclosures, child marks, or sibling marks. Axes, lane names, current-time marker, and viewport selection window may remain as navigation scaffolding. Independently matching parents and children are each counted by their own canonical ID; a child match does not make its parent or siblings matches. Authorized ancestor context in detail remains separately flagged and excluded from finding counts/implicit selections.
- Grouping changes arrangement, not the match predicate. Applying a saved filter, source scope, or explicit time predicate recomputes `B` and `M` together; search never reveals excluded or unauthorized records. Overview remains usable under every supported grouping and camera mode. Empty lane shells may be retained for a stable layout, but may not imply hidden record counts are findings.
- Table behavior must be explicit: its default contextual mode displays `B` and marks finding rows; an explicitly selected matches-only mode displays `M`. Counts must distinguish filtered records from search findings. Exports and bulk actions name their scope (`selected IDs`, `all filtered`, `search findings`, or an explicit range) and preview it; highlighting alone must not silently redefine a destructive operation's target set. Both views use the same record snapshot even when their display projections differ.

### Safe Matching and Highlight Lifecycle

- Recommended legacy-compatible multi-term mode is **Any term**: trim input, separate terms on whitespace/semicolons outside quoted phrases, discard empty terms, and match literal substrings using Unicode normalization and case-insensitive comparison by default. Quoting preserves a phrase as one term. Terms `5_1` and `0_3` retain literal underscores. An explicit **All terms** mode requires every term to match that record, and an explicit **Phrase** mode treats the entire query as one phrase under the documented versioned grammar. Name the mode in UI/API state; do not guess mode from punctuation. The grammar must define literal-quote and backslash escaping consistently across modes and reject unmatched quotes or malformed escapes with actionable errors. Limit input to 512 characters and 20 terms; also document bounds for field count and execution work.
- Search title and description plus explicitly declared searchable scalar fields in the effective schema. An optional field selector may enable record IDs or other authorized fields; do not search serialized JSON keys, credentials, hidden fields, or rendering metadata implicitly. Define scalar and missing-value handling; searchable arrays require an explicit versioned policy, never implicit serialization. Case-sensitive matching is an explicit option. Regex metacharacters, `*`, ampersands, and plus signs are literal search data, never executable patterns or accidental URL syntax. Quotes and backslashes have only their declared phrase/escape roles; escaped quotes remain literal data, not executable syntax.
- The whole matching label background is yellow `#F8DF09` with a contrast-checked dark foreground. Keep normal event/session fill and duration geometry unless an independent style rule applies. A matched-field indicator or accessible finding announcement supplements color. Selection, hover, focus, and validation overlays must remain distinguishable and must not erase the match indication.
- Store search membership outside canonical `render` overrides. Search requests, previews, navigation, clearing, and highlight rendering are read-only: record versions, stored JSON, audit mutation history, and persisted authored styles do not change. Clearing restores the exact effective label style from model/record rules, including previously authored yellow backgrounds, not a guessed default.
- Enter and the search icon apply the same draft query. A clear command immediately applies the empty query. Applying/clearing preserves viewport, grouping, filters, and selection unless selected records cease to be authorized. Finding navigation is explicit, deterministic by start time then ID, and uses the same pinned result set; it may move the viewport only when invoked. Disable next/previous at zero findings and document boundary behavior rather than silently wrapping.
- Zero findings means zero overview record marks and a compact zero-result state; detailed filtered context remains. Errors are not zero results. Retain the previous valid result with an error/stale indication or show a clearly unavailable state; do not combine old highlights with new counts. Cancel/ignore superseded responses by instance, query, generation, and snapshot identity. Permission changes must invalidate unauthorized results and counts immediately under the shared authorization contract.

These contracts deliberately correct unsafe legacy behavior. The final prompt/API schema must choose and encode the recommended modes and scope explicitly; compatibility does not require preserving raw regex, omitted parent matching, or accidental color-based membership.
